# Load-bearing claims: adversarial verification

36 factual claims that the top ideas depend on were extracted and handed to four skeptical fact-checkers (codebase, pmndrs/math, R3F/three/pmndrs packages, web platform). Each was told to try to refute the claim and to mark it confirmed only with decisive evidence. Result: 10 confirmed, 26 partly true (needs a qualification), 0 fully refuted, 0 unverifiable. The qualifications matter: several change what an idea can promise.

## Lupi codebase

### K01 · Partly
**Claim:** The v9 atom vertex shader in packages/scene/src/AtomsOptimized.tsx computes `mix(instancePosition, instanceTargetPosition, uProgress)` (~L342-367, uProgress clamped to [0,1] in JS ~L1576), and packages/scene/src/bondImpostor.ts L56-57 lerps bond endpoints the same way. So a condense, burst, recycle or normal-mode extremes animation can run on v9 with zero GLSL changes: upload a 'from' frame and the true frame as the two endpoints, then drive uProgress from TypeScript. Three consequences: the clamp rules out overshoot on v9; a single uniform rules out per-atom stagger; and the path must not collide with trajectory playback (useSmoothFramePlayback and the interpolation.ts PBC unwrap), which owns uProgress today.

**Ideas that depend on it:** C030, C077, C118, R2-first-minute-flagship-01, R2-first-minute-flagship-04, R2-first-minute-flagship-14, R2-port-as-toy-engine-02, R2-real-twins-science-05, R2-real-twins-science-10, R2-real-twins-science-11, R2-signature-and-moonshots-07, R2-signature-and-moonshots-11 (v9 slice), R2-capture-share-loops-11, R2-capture-share-loops-13

**Evidence:** packages/scene/src/AtomsOptimized.tsx:342,367 (uniform uProgress; mix(instancePosition, instanceTargetPosition, uProgress)); :1570-1576 (useFrame writes a clamped uProgress every frame, 0 whenever !canInterpolateToNextFrame); :1202-1205 (canInterpolateToNextFrame = nextFrame && framesShareAtomOrder(frame,nextFrame)); :1650-1709 (targets uploaded only from nextFrame with wrapDelta PBC unwrap, otherwise mirrored). packages/core/src/frameIdentity.ts:33-43 (requires source-id/source-order identity); packages/parsers/src/xyzParser.test.ts:16 (XYZ frames are 'synthetic-row'). packages/scene/src/bondImpostor.ts:37,56-57 (same mix). Other uProgress writers: packages/scene/src/Bonds.tsx:857-863, VectorGlyphs.tsx:365-371, both clamped and rewritten every frame. Bonds.tsx:494-509 (bond pairs are inferred from `frame`, the 'from' endpoint). AtomsTransmission.tsx:17,175 (the transmission path lerps on the CPU, not through uProgress). AtomsOptimized.tsx:185-188 (the culling sphere assumes a clamped uProgress).

**What is actually true:** Zero GLSL changes is right: both shaders already mix two endpoint buffers by one uniform. 'Drive uProgress from TypeScript' still takes real TS plumbing, for four reasons. (1) The existing useFrame hooks in AtomsOptimized, Bonds and VectorGlyphs write uProgress on every frame. For a single-frame file such as caffeine they force it to 0, so a value set directly is reset on the next frame. It also can't just be passed as a prop, because interpolationFactor is ignored whenever liveStateRef is set with a frameIndex. (2) The endpoint pair is uploaded only when framesShareAtomOrder(frame, nextFrame) is true. That rejects the 'synthetic-row' identity that XYZ, PubChem and similar loads carry, so a from/true pair needs a stable identity or an explicit override. (3) Bond topology is inferred from `frame`. If the seeded cloud is `frame`, bonds are inferred on the cloud. The true frame must therefore be `frame`, with uProgress run 1→0, or the topology pinned. (4) With transmission recipes active, atoms go through AtomsTransmission's CPU lerp, not uProgress. Consequences: the clamp does rule out overshoot today, but the fix is a TS change plus a wider culling sphere, not shader work. Per-atom stagger does need GLSL or an extra attribute. The collision with useSmoothFramePlayback/wrapDelta ownership is real, and it is larger than stated, because the owner writes uProgress even for static files.

### K10 · Confirmed
**Claim:** In math@0.1.0, spring.update(state, target, smoothTime, dampingRatio, delta), and the same function in spring2/3/4, applies the exact closed-form damped-oscillator solution as a 2x2 linear map (pp, pv, vp, vv). It is therefore stable at any delta with no clamping, and for a fixed target, N steps of delta/N match one step of delta up to float rounding. **Ideas that depend on it:** C003, C021, C002, R2-first-minute-flagship-03, R2-first-minute-flagship-08, R2-first-minute-flagship-09, R2-first-minute-flagship-10, R2-capture-share-loops-03, R2-capture-share-loops-04, R2-port-as-toy-engine-11, R2-port-as-toy-engine-12, R2-play-for-everyone-10

**Evidence:** git show math@0.1.0:src/time/spring-core.ts L15-51: `coefficients()` writes an exact 2x2 map {pp,pv,vp,vv} with critical (|ζ-1|<1e-4), under- and over-damped branches, and never clamps delta. spring.ts L35-40 and spring2/3/4 `update(state,target,smoothTime,dampingRatio,delta)` apply it per component. The npm tarball matches (shasum 647aa2b7… = npm dist.shasum for 0.1.0). Test scratchpad/kcheck/k10.mjs, run against the published dist: with a constant target, 30/60/120/240 Hz for 1 s agree to within 1e-14 for ζ=0.3, 1 and 2.5, and 1 step of 1.0 s vs 1000 steps of 1 ms differ by at most 4e-14.
